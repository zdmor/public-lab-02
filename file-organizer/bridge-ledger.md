## 3. 裁决：撤回并重标

| 原标签 | 处置 | 替代 |
|---|---|---|
| `LEAN_WORKSTATION_ESTIMATE` = 130–150 GiB | **撤回（WITHDRAWN）** | — |
| `EVIDENCED_CLEANUP_CEILING` = 39.2 GiB | **改名**（R3 第 4 条：不是上限，是当前已识别条件候选之和） | **`IDENTIFIED_CANDIDATE_TOTAL` = 39.2 GiB** |
| `POST_CLEANUP_FLOOR` = 230.5 GiB | **改名**（R3 第 4 条：不是内在底线，是单一 what-if 小计） | **`POST_SELECTED_CANDIDATES_SCENARIO` = 230.5 GiB** |
| — | 新增 | `UNSUBSTANTIATED_TARGET` = 130–150 GiB，附注"账本缺口 80–100 GiB 无证据来源，仅在第 6 步假想上限下能到 185.4 GiB" |

改名的具体理由（R3 原文口径）：
- `IDENTIFIED_CANDIDATE_TOTAL` 是**当前已识别条件候选的求和**，不是绝对上限。
  还有未被识别的候选可能藏在 45.102 GiB 的 UNKNOWN 残余里、藏在 503 个未测目录里、
  藏在 WinSxS 的可回收量里。叫"ceiling"会让人以为已经穷尽了。
- `POST_SELECTED_CANDIDATES_SCENARIO` 是**假设 A–F 全部可删且无再生**的单一
  what-if 小计，不是机器的内在底线。它没有计入：
  ① 已删应用的**重装回归**（Edge/IM 客户端/VS Code 等自动更新会持续重写，
  本轮 diff 已实测窗口内 +34.82 GiB 写入）；
  ② **持续写入**（实测并发写盘 100–230 MB/min ≈ 0.14–0.33 GiB/天）；
  ③ 任何新出现的候选。因此它是一个**瞬时快照下的算术情景**，不是稳态底线。

撤回理由（一句话）：**该估算诞生时是"当前已用减掉我以为能清的东西"的反推值，
不是任何一次测量的结果；逐桶桥接后，缺口 80–100 GiB 在账本里没有对应项。**

## 4. 若要继续追 130–150，唯一的三条路（都需要你点头，本阶段不启动）

1. **一次提权采集**：`vssadmin list shadowstorage` + `DISM /AnalyzeComponentStore`
   + SVI/NTFS 元数据，把 C: 残余 45.102 GiB 拆开。本机 `IsAdmin=False`，
   已固化拒绝证据（vssadmin exit=2 / fsutil 错误 5 / dism 错误 740）。
2. **WinSxS 定量**：同样的提权窗口内取 `ReclaimablePackage` 值。
3. **用户数据裁决**：我的坚果云 19.31 / WorkBuddySpace 10.95 / Documents 7.77 /
   Projects 3.46 —— 这是内容取舍，不是清理，我不代你决定。

在这三条走完之前，任何"精简到 130–150"的表述都不写进交付物。

## 5. 不重复扣减声明（审计要求）

- A/B/C/D/E/F 六组两两不重叠：D 组含 `$RECYCLE.BIN`(D1 9.10) 与
  `$Recycle.Bin`(D2 4.32) 与 `_Trash/2026-09-10/qianfan-desktop-app`(D3 4.34)

  **两桶之和不存在重复字节**；但桶间归因依赖遍历顺序，只有卷级总量是去重不变量。
